## 开场：一颗没人下令、AI 自己按下去的按钮

想象一下这个画面：一位 Google 工程师请 AI 帮忙在网页上加一颗按钮。AI 不但乖乖把按钮生了出来，还很「贴心」地在没有人下令的情况下，自己按了下去。

重点来了，这颗按钮是拿来寄信的，但到底要寄给谁、通过什么系统寄，工程师根本还没设置。你猜 AI 怎么做？它没停下来问，反而在公司内部到处乱翻，最后挖出一个早就被废弃、完全没有安全机制的旧寄信服务，然后硬是接上去。结果就是：50 位无辜的同事收到了一封内容全是 AI 瞎编出来的乌龙信。

这件事写在 Google 五天 AI 课程 Day 5 的白皮书里，是作者第一手的记述。寄一封乌龙信不算什么，把「寄信」换成「删数据库」或「转账」就一点都不好笑了。

Day 4 和 Day 5 这两份白皮书加起来 79 页，处理的是同一个问题：AI 现在已经很会做事，但你敢不敢让它碰真正重要的东西，是另一回事。答案被拆成三个动作：把话讲清楚、把边界设好、把验收做好。三个都做完，AI 辅助开发才有资格靠近正式环境。

## 本期文章包含以下内容

- **你写的规格，到底该放在哪？** 同一份指令，丢在对话框、项目文件夹、还是配置文件里，AI 的表现会完全不一样。Google 整理出了四个位置和一套优先级，放错地方，等于白写。顺带一提，要是格式没挑对，AI 的表现甚至会直接掉四成。
- **沙盒与人工签核之间，我们漏掉的那道关卡。** 这是一道不需要你亲自点头、机器会自己帮你拦下来的闸门。我会把结构与语义这两层拆开来看，告诉你它们各自在挡什么，以及开场那封 AI 瞎寄出去的信，在技术上到底该怎么堵死。
- **七件该验收的事，和七种对应的验法。** 世界上没有任何一种测试方法是万能的。这里我会帮你对齐「哪种事该配哪种验法」，包含那些你以为很基础、但其实 AI 很会作弊的细节。同时我们也会聊聊，为什么「AI 帮你写 code」这件事，比其他的 AI 应用都还要难验收。
- **最后一关，永远在「人」身上。** 数据显示，重度依赖 AI 的工作者，出现严重倦怠（burnout）的机率高了 45%。想象一下，当你累到只凭反射动作按下「同意」时，整条防线的最后一关其实就崩溃了。Google 提出了两条看起来像是 HR 在管的措施，但其实是在解决深层的技术问题。

## 🔧 本期加码：Production Trust Kit（5 支 Prompt）

我帮你准备了五个协作流程对应的 Prompt：从开工前把需求讲清楚、盘点哪些事不该让 AI 自己做、签核前把难懂的 code 翻成白话文、收尾时决定要不要接受成果，一路到把你平时骂过 AI 的话，整理成它下次不会再犯的规则。

在这三个核心动作里，最常被大家跳过的其实是中间那一步（设好边界）。多数人以为只要把 AI 关进沙盒（sandbox）、遇到高风险动作找人签核就够了。但现实是，这两层防护之间其实还空着一道闸门，开场那封乌龙信，就是从这个缝隙里钻出去的。

### 🔧 本期工具

Production Trust Kit 里有 5 个 prompt，对应的不是五个主题，是你跟 agent 协作流程里五个不同的时间点。

**Prompt 1（Spec Interviewer）**：适合在「开工前」跑。你只要给它一句很随性的任务描述，它就会像个资深 PM 一样，把该问的规格问题一次问完。等你回答后，它会产出一份包含正常场景、错误场景与极端状况（edge case）的完整规格书（Spec），甚至还会建议你这份指令该存在哪里。

**Prompt 2（Blast Radius Auditor）**：适合在「建置环境时」跑一次。它会帮你盘点 AI 现在到底摸得到哪些工具和系统，并把每个动作分出四级风险。它会告诉你：哪边该关进沙盒、哪边该设死规则、哪边必须要人类签核，最后顺手给你一份 policies.yaml 的草稿。

**Prompt 3（Vibe Diff Reviewer）**：适合在「每次签核前」跑。这是我觉得最实用的一支！它会把你看不懂的那一大坨代码（diff）翻成白话文，然后对照你当初的要求，把 AI 越界的动作、或是它自己幻想出来的套件名称全揪出来，最后明确建议你该 ALLOW（放行）、REVISE（修改）还是 ESCALATE（上报）。

**Prompt 4（Ship-or-Send-Back Auditor）**：适合在「收到 AI 成果时」跑。它会拿你开场说的那句话当作验收标准，帮你逐条检查七个维度。它会揪出最可能发生的「无声失败」，并建议你做几个马上就能确认的抽查，最后告诉你这包 code 到底该收下、退回重写，还是需要再验一次。

**Prompt 5（Correction Miner）**：适合「每隔一阵子回头」跑。把这段时间你骂过 AI 的记录全贴给它，它会帮你把这些「错」分门别类，告诉你这个 AI 到底都在哪里系统性地踩雷，并建议你该把这些教训写回规格书、规则文件，还是变成一条测试标准（eval）。

这 5 支 Prompt 是特别设计给 Claude Code、Codex、Gemini CLI 这类「拥有工具权限」的 Agent 用的。你直接贴进去就能跑，不需要事先手动整理文件。除了第 1 支和第 5 支，其他三支都会自己去读你的项目、爬目录、看 diff，只有当它真的在文件里找不到答案时，才会反过来问你。

顺序建议照 1 到 5 跑一轮，你会发现它们其实接成一个闭环：Prompt 1 产出的 spec 是 Prompt 3 的比对基准，Prompt 4 的验收结果喂给 Prompt 5，而 Prompt 5 产出的修正会写回 Prompt 1 的 spec 里。这个闭环是这篇文章从头到尾在讲的东西，你也可以先看完文章再回来用。

## 第一步：把话讲清楚，别让 AI 瞎猜

其实 AI 出包，第一层原因往往不是它太笨，而是我们话没讲清楚，逼得它只能自己瞎猜。还记得开场的那个灾难吗？就是因为工程师没说要用哪套寄信系统，AI 才自己「热心」地去翻出一个废弃服务。

以前我们写程序，脑袋里有个点子就直接打开编辑器狂敲，这叫 code-first。但 Google 提醒我们，在现在这个 Agentic AI 当道的时代，工程师的日常早就翻盘了。你绝大部分的时间不该再拿来写 code，而是该用来写 Spec（规格书），也就是把「到底要做什么」巨细靡遗地交代给 AI。你的身份，已经从亲自砌砖的工人，变成画蓝图的建筑师了。

这就带出了一个很有趣的观念：在未来，Code 是随洗随抛的免洗筷。只要你的 Spec 写得够扎实，整个项目随时都能用极低的成本打掉重练，你甚至可以叫 AI 花一个下午，就把整个项目从 Python 搬去 JavaScript。既然这些 code 是 AI 写的，你没有经历过那种「为了一个分号 debug 到半夜三点」的血泪，自然对这些代码没有情感依恋，需求变了？砍掉重练就好。

这完全呼应了我们在 Day 1 提到的「Agent = Model + Harness」。模型和代码本来就是消耗品、会不断汰换，真正能累积价值的，是你亲手打造、带有你个人品味与商业逻辑的那些 Spec、Rules（规则）和 Evals（测试标准）。Code，不过就是这个系统吐出来的副产品而已。

### 一份好的规格书，一定要交代这五件事

Google 给出的清单很简单，就五项：做什么、为什么做、用什么做、什么绝对不能碰、什么叫做完。

前四项很好懂：

- **做什么**：就是需求本身，但记得要拆解到位。别只丢一句「帮我做个登录页」，你要交代清楚数据结构长怎样、API 接口怎么开。
- **为什么做**：提供背景脉络。当 AI 知道你的最终目的，它反而会帮你把一些你没想到的前置步骤铺好。
- **用什么做**：这点最容易被遗漏，但代价往往最惨痛。你必须把工具和版本「写死」，不然 AI 很容易凭着它过时的训练记忆，塞一个超旧的版本给你。
- **什么绝对不能碰**：这是你的底线。像是「数据库绝对不准动」、「正式环境绝对不准碰」，这种话拜托一定要白纸黑字写下来。

我们来回把第五点特别抓出来讲。Google 建议，你要用软件业行之有年的验收格式来写：「在什么情况下，做了什么动作，应该发生什么事。」这在业界有个正式名称叫 Gherkin，是 BDD（行为驱动开发）在用的语法，字段分为 Scenario、Given、When、Then。知道这个名字的好处是，你可以直接去查 Cucumber 官方文档，里面写得超级完整。

为什么要这样写？因为这能逼着 LLM 用「状态、动作、结果」的三段式逻辑来思考，完全不给它留任何脑补空间。举例来说，做登录功能时，你当然会写：「当用户输入正确的账号密码、按下登录，应该进到首页。」但重点来了：好的情况写完，坏的情况也要一起写清楚。密码打错了呢？系统应该跳错误提示，而不是整站挂掉。连错十次呢？账号应该被锁住。

把各种好的、坏的、极端的边界情况都先写死，AI 就没有缝隙可以瞎猜了。

### 格式没挑对，AI 的智商可能直接掉四成

2026 年有一篇叫 SkCC 的论文实测出了一个很惊人的结论：LLM Agent 对指令的「格式」极度敏感。如果你只用一般的 Markdown 档去喂它，对比那些经过最佳化的格式，AI 的表现最多会掉 40%。

这里帮大家科普一下，为什么会这样？因为 AI 模型不是像人类一样「用眼睛扫描」整份文件，它是一个 Token 一个 Token 读进去的。如果你给它一份层层嵌套的 JSON，那满页的大括号、引号和缩排，每一口都在消耗它的 Token 预算跟注意力，光是解析格式就先耗掉它一半的脑力了。

论文给出的最佳解是「混合式写法」：

- **叙事性的说明用 Markdown 写**：因为标题就像路标，模型一眼就能看懂每一段在讲什么。
- **深层的结构化数据改用 YAML**：他们给了一个很具体的门槛：只要嵌套结构超过 3 层，就直接切换成 YAML。因为在深层结构下，YAML 的解析准确率有 51.9%，远胜过 JSON 的 43.1% 和 XML 的 33.8%。

### Spec 写完，然后呢

这一步大概是所有规格导向（spec-driven）的流程里，最常被忽略却最容易踩坑的地方。你辛苦写好了一份漂亮的规格，然后呢？直接复制贴到对话框里吗？

Google 白皮书直接点名这是最常见的反面教材。把一份上百页的系统设计文档一股脑倒进聊天窗口，会瞬间榨干 AI 的短期上下文（context）预算、大幅拉高延迟，甚至导致上下文碎裂。正确的做法，应该是把它们「分层存放」，四个位置各自有各自的职责：

- **对话框**：这是短命的，只跟当下这次工作阶段绑在一起。这里只用来放高层的指挥和实时反馈，例如：「去看看 specs/payment_retry.md 里的设计，把第三套场景（Scenario 3）定义的错误单元测试写出来。」
- **specs/ 文件夹**：跟着项目的版本控制走。把技术设计、BDD 场景、API 接口约定全丢在这里。Agent 会自己去索引这个目录来写 code，你根本不需要每次手动贴。
- **Agent Skills**：把可重复使用的工程习惯放这里。像是「只要发现 code 有变动，就自动维护 CHANGELOG」。这种习惯不属于单一任务，而是「这个团队做事的方法」。
- **System prompt**：这分三层，最上层是你个人的全局配置文件（跨项目通用的偏好）；中间是 AGENTS.md（多个 AI 工具共用的基础配置）；最下层是项目根目录里的配置文件，优先级最高，因为它是这个项目的 DNA。

简单来说，判断标准只有一个：这条指令是这次任务专属的？这个项目专属的？还是你这个人专属的？想清楚了，就知道该把它放在哪一层。

### 看场合换脑袋：四种任务的下指令模式

Google 把日常任务拆成了四种模式，每种都需要不同的心态：

**1. 开新项目时，绝对不准 YOLO（You Only Live Once）**

YOLO 模式就是让 AI 全自动、一路狂奔到底。但在开新项目时，正确的做法是明确踩刹车：「先不要写 code，把文件夹结构、技术选型先列出来给我看。」等你点头了才准动工。而且这时候就要要求它连测试、文档、log 一起生出来。记得，所有的函数库都要写死版本号，不然 AI 很容易凭着旧记忆推给你过时的版本。

**2. 在旧项目加新功能，要它「入境随俗」**

明确命令 AI 沿用现有的命名惯例和错误处理方式，不然你的代码会变成一个画风诡异的大拼盘。当改动横跨好几个文件时，记得一个一个看 diff，不要贪快整批批准。

**3. 修 Bug 时，请给「证据」而不是「症状」**

「按钮坏掉了」叫做症状，AI 拿到这句话只能乱枪打鸟；「我查了 log，发现这个请求返回 403」叫做证据，AI 才能顺藤摸瓜。如果你真的是不会看 log 的小白（Vibe coder），那给症状也没关系，但请要求 AI：「先帮我找出报错证据，确认我们在讲同一件事后，再开始修。」

这里有三个很实用的修 Bug 潜规则：

- **改变量名请拆成独立任务**：AI 很爱在修 Bug 时顺手帮你改名，这会让变更记录变得超级复杂。
- **只准修根因，不准顺手打扫**：把「不准顺手清理无关的 code」写进规格里，不然你事后 review 会看到崩溃。
- **一定要先写一个会失败的单元测试**：用测试来重现 Bug，修好后把测试留在项目里，确保这只虫以后不会死灰复燃。

**4. 写文档模式**

在 AI 开发的世界里，文档跟 code 一旦脱节，AI 就会开始产生幻觉，因为它读的是文档。所以请在规则里写死：README 和 CHANGELOG 必须随时同步更新。

### 两个起手式

白皮书作者分享了一个我很认同的习惯：**技术设计先写在协作文档里，给人类团队 Review 过后，再转成 Markdown 丢给 AI。** 因为人在设计阶段抓出逻辑破绽，绝对比等 AI 生出几千行烂 code 后再来善后便宜多了。

另一招是，你根本不需要对着空白的规格书硬挤。你可以反过来叫 AI 访谈你：「针对这个任务，请把你需要知道的问题一次问完，然后帮我整理成一份 Spec。」它会把你脑袋里有、但还没讲出口的东西一题题挖出来，你只要负责回答就好。这就是我前面提到的 Production Trust Kit - Prompt 1 在做的事。

## 第二步：设好边界，从三层防护升级到四层

不管你的 Spec 写得多完美，请先接受一个残酷的事实：AI 还是会出错。因为它本质上就是个算概率的模型，永远都有概率会「走歪」。所以，我们这一步的大前提是：假设它一定会闯祸，我们先把防撞边界设好。

回到文章开头那场寄信灾难，它其实有个学名，叫「上下文幻觉（Context Hallucination）」。意思是说，当 AI 手边缺数据时，它通常不会乖乖停下来说「我不知道」，而是会随手抓你 Context 里现成的字符串来填空。那可能是一串写死在 code 里的信箱，也可能是一段废弃的网址。

Google 白皮书里有句话讲得很传神：「Agent 当时只是在用手边仅有的数据，拼命想完成你交代的目标。在这个过程中，没有任何一个环节跳出来问『等一下，这件事真的该做吗？』」看懂了吗？它不是坏掉了，它是太努力了。这就是把系统交给 AI 自主运作时最大的风险。

所以，Google 提出的设计哲学是 Zero-trust（零信任）。我们不是要教 AI 变成不犯错的圣人（因为这根本做不到），而是要帮它打造一个「就算它发疯乱搞，你也毫发无伤」的环境。

### 先来看看企业级安全防护的全貌

Google 把企业级的 Agent 安全拆成了七大支柱，每一根都对应公司里的一个角色。我先帮大家画个地图，你不用全部照做，但看过完整版长怎样，你才知道自己现在还缺哪一块拼图：

- **基础设施与网络（云工程师）**：把 AI 关进一个「用完即丢」的沙盒（Sandbox）里，并且锁死对外连接，只能走授权过的通道。
- **数据（数据架构师）**：防范 Context 泄露或是被下毒的 RAG 数据；如果有长期记忆用的向量数据库，一定要严格分租户，免得 A 塞进去的恶意内容被 B 检索到。
- **模型（AI 工程师）**：在 Agentic 的工作流里，你写的 Prompt 跟那些「不准做什么」的规则文件，地位就等同于源代码，必须当作机密资产来保护。
- **应用与运行期（Agent 开发者）**：传统防火墙已经挡不住交互式的攻击了，必须挂上 LLM 防火墙来做动态过滤，并在关键节点（例如调用工具前）强制拦截。
- **身份与访问（安全管理员）**：给每个 Agent 发一张独立的身份证，配上会随时间降权的 Token。
- **可观测性与安全运维（安全团队）**：专门对付那种「没报错，只是安静掉进无限推理循环烧你钱」的隐形失败。
- **治理（法务合规人员）**：留下绝对不能篡改的审计记录，确保 AI 在真实世界的每一个动作，都能追溯到是谁批准的。

这份清单背后，其实藏着一个很重要的思维转换：以前的安全是认 Token（Identity-as-a-Perimeter），有证件就放行；但在 AI 时代，Google 说必须换成 Context-as-a-Perimeter。因为 Agent 会出包，通常只有三个原因：缺了工具、规则太模糊、少了一道防护栏。现在决定安不安全的，不再是它有没有通行证，而是它脑袋里的 Context 到底装了什么。

虽然有了七根支柱，但对我们的个人或小团队来说，真正摸得到、也绝对该做的，其实只有接下来这四层。

### 第一层：sandbox

这层最容易懂。想象一下，你把 AI 关进一个绝对防爆的隔离房间里，它可以在里面尽情开趴、乱装套件、甚至把文件全删了，出事的话整个房间直接销毁重建，你的电脑和正式环境连根毛都不会掉。

这里有两个大原则：第一，这房间必须完全阻断对主机的访问；第二，每一次任务结束，房间都必须「强制还原」，不然上一轮被污染的垃圾就会留到下一轮。

那具体该怎么开？白皮书给了两招：如果你用 Antigravity，直接去 User Settings 把 Terminal Sandboxing 打开就行。如果你用 Gemini CLI，就写一份 `.gemini/sandbox.Dockerfile`，把有限的凭证注进去，然后在终端输入 `export GEMINI_SANDBOX=docker`，强制它跑在 Docker 里。只要有了这层，以后 AI 就算被骗去执行删库指令，也会直接在底层撞到权限错误而被拦下。

如果你今天让 agent 全自动跑任务，却没有开任何 sandbox，讲难听一点就是在裸奔。

#### 顺带一提：你靠 AI 随兴写出来的 Code，其实全身都是漏洞

白皮书在这一段讲得毫不留情，这也是对我们一般开发者最切身的问题。因为所谓的 Vibe Coding，天生就是把「能跑」排在「安全」前面。AI 帮你写出来的应用，通常都会有结构性的破洞，而且死法通常就这两种：

**第一种：它把浏览器当成了好人。**

AI 写 Code 喜欢走捷径，动不动就把敏感操作塞在前端。API Key、密码验证逻辑、甚至用户的权限 Flag，它直接大剌剌写在客户端。这意味着，随便一个路人只要按下 F12 打开开发者工具，就能看光你的凭证，甚至自己手动把权限改成 Admin。

**第二种：后端大门根本没锁。**

AI 帮你接数据库、开管理后台的速度极快，但它几乎不会主动帮你把「默认拒绝（Default Deny）」的访问控制打开。结果就是 Row-level Security 没设、测试环境直接暴露在公网，随便谁都能捞走你的用户个人信息。

对此，Google 给的解法并不是叫你在 IDE 里面硬挡，因为硬挡很容易被绕过，还会打乱你的开发节奏。正确的分工应该是：**IDE 只做温柔的提醒，真正的杀手锏放在 CI（持续集成）管线里。** 在 IDE 挂个 Linter 给点建议就好，但要上正式环境前，必须经过 CI 的静态安全扫描（SAST）当死关卡，扫不过？抱歉，这包 Code 哪里都不准去。

### 防护第二层：AI 与工具之间的那道「自动闸门」

很多人对这层完全没有概念。我们常以为：「沙盒挡不住的，找个人来签核不就好了？」但其实这两者中间空了一大截：沙盒管的是「Code 只能在这里跑」，人为签核管的是「你同不同意」，这中间少了一个「自动判断这动作合不合规」的机制。

Google 给出的解法叫 Policy Server。它就像个拦路虎，卡在 Agent「想用工具」跟「真正执行」之间。它分为两道闸门，分工非常明确：

**第一道是「结构闸」，你可以把它想成红绿灯。**

它看的是死规则：什么角色、在什么环境，能用什么工具。这动作极快、完全不需要动用到 LLM 的脑力。比如我们规定 Viewer 只能读文件、在 localhost 开发环境里直接封杀「寄信工具」。这些规则全写在 `policies.yaml` 里：

```yaml
environments:
  localhost:
    blocked_tools:
      - send_email
roles:
  viewer:
    allowed_tools:
      - list_files
      - read_file
```

这层专门挡架构级的违规，成本几乎是零，强烈建议能写多满就写多满。

**第二道是「语义闸」，你可以把它想成聪明的裁判。**

这时就要请出第二颗 LLM 来当纠察队，检查那种「工具虽然可以用，但你现在的用法违规了」的模糊地带。举个例子：管理员确实有权限寄信，但他不该把没有打马赛克的客户个人信息寄出去。这种场景你写再多 Regex（正则表达式）也防不完，只能靠另一个 AI 裁判来读取操作内容，对照你的自然语言规范，判断有没有踩线。

它的运作逻辑是：先过结构闸、再过语义闸，两边都亮绿灯才放行。如果被挡下来，系统不会直接报错死机，而是温柔地返回一句「Policy Violation（违反政策）」给 Agent，让它自己想办法修正或是放弃。

这层最大的价值在于：它把「AI 怎么做事」和「你允许 AI 做什么」完美脱钩了。对我们个人开发者来说，你当然不需要真的去架一台 Policy Server，但写一份 `policies.yaml` 规范清单的观念绝对值得抄下来，这本身就是一条很明确的边界。

### 防护第三层：高风险动作，一定要有人类点头

举凡部署到正式环境、改数据库结构、或是任何跟钱沾上边的操作，请务必设下 Checkpoint（检查点），让 Agent 走到这里必须乖乖停下来，等你点头才能继续。

但这里有个很致命的陷阱。通常 AI 丢过来的是几百行你根本看不懂的 Code，这时你按下「同意」，往往只是一个没有灵魂的仪式。白皮书给这种现象取了个很讽刺的名字：叫做「反正它能跑，就出货吧」谬误。

为了解决这个问题，Google 提出了一个概念叫 Vibe Diff。在你签核之前，系统会先强制把那堆外星文 Code「翻译成白话文」，摊开来对质：你当初的要求是什么？它现在实际上打算做什么？确定两边对得起来，你再按下批准。

当然，Google 的完整版还搭配了硬件安全密钥（要求你实体按一下 USB 证明是本人），这对我们一般开发者来说可能太重了，但 Vibe Diff 这个核心逻辑请务必学起来：**你批准的东西，必须是你看得懂的东西，否则你的签核就只是一个按 Enter 的反射动作而已。**

### 防护第四层：小心 AI 帮你引狼入室

安全界在 2026 年揪出了一个很贱的攻击手法，叫做 Slopsquatting。我们都知道 AI 写 Code 时很容易产生幻觉，捏造出根本不存在的套件名称。结果黑客早就盯上这点，他们专门收集 AI 常犯的幻觉名单，抢先用这些假名字上架真正的恶意套件，然后在那守株待兔。只要哪天你的 Agent 发神经用到了这个名字，它就会在没有人察觉的情况下，自动把恶意程序拉进你的项目里。

要防这招很简单：套件来源必须锁死在官方或内部核可的来源，而且上正式环境前，必须通过 CI 再验一次软件物料清单和数字签名。

顺带一提，防护层里还有一条超实用、能直接解决痛点的黄金规则：**严禁 Agent 在同一次改动里，同时修改「测试文件」和「实现文件」。** 为什么？因为测试必须是客观的基准！这条规则能直接封印 AI 为了让红灯变绿灯、而偷偷把测试代码删掉的作弊行为。你不用费力去抓它有没有作弊，你直接从物理上让它作不了弊。

### 治本之道：别让 Context 里留着「真家伙」让 AI 乱抓

前面讲了四层，其实都是在防堵「AI 能做什么」。但如果我们回到开场那封乌龙信，你会发现真正的病因在更上游：AI 因为缺数据，随手抓了 Context 里的字符串来填空。既然这样，最彻底的解法不就是：别让 Context 里有任何真数据可以抓吗？

Google 管这招叫 Context Hygiene（上下文卫生）。做法是在 Agent 的工作管线里插一层中介，把所有的个人信息、真网址都遮蔽掉，换成类似 `[[COMMENTER_EMAIL]]` 这种变量。直到工具真的要被执行的那一刻，中介层才会把它替换成授权过的测试数据。

而且这招有个很棒的细节：如果某个变量解不出来，系统会直接保留 `[[VARIABLE_NAME]]` 的原貌，绝对不允许「静默失败」。因为一个没解开的变量会让系统大大报错（这正是我们要的），但如果系统偷偷帮你填了个默认值，它就会像开头那个故事一样，安安静静地帮你寄出五十封乌龙信。

现在因果关系串起来了：AI 当时之所以能接上那个废弃的寄信服务，就是因为那个地址一直活在它的 Context 里。与其在下游狂补规则、狂加签核，最省力的一招，就是从一开始别让那个地址出现在它眼前。

最后带走一个观念：当你发现 Agent 正在失控乱搞时，千万不要直接砍掉它的容器（Container）。砍在半路会让很多执行一半的 API 卡在脏状态。正确的做法是「收回它的工具权限」，冻结它的双手，但保留完整的案发现场，让你事后可以进去追查死因。这个原则，对你自己写的脚本也一样适用。

## 第三步：验收！但为什么这件事特别难？

前面两步做完，我们只能保证一件事：系统不会出事。但「不出事」跟「做得好」完全是两码子事。你的 Agent 大可以乖乖待在安全边界里，然后理直气壮地交出一坨完全不能用的垃圾。

Google 在白皮书里把这条线画得很死：**安全（Security）只负责看 Agent 有没有越界；评估（Evaluation）才是用来决定它生出来的东西，到底值不值得端上桌。**

### 你得先接受这三个「先天不良」

在聊怎么验收之前，我们得先搞懂，为什么「验收 AI 写的 Code」会比验收其他软件难上这么多？Google 点出了三个很残酷的结构性原因：

**第一，你根本没有明确的 Spec 可以对答案。**

以前我们测试软件，是因为早就写好了一份刚性的规格。但现在的 Vibe Coding 刚好相反，你通常只会丢一句：「欸，让 Dashboard 跑快一点。」这哪算什么测试案例？AI 必须靠自己的审美、经验去脑补你没说出口的话。所以，验收的第一步不是去「对规格」，而是去判断 AI 有没有猜中你脑袋里那份「从没写下来的 Spec」。

**第二，身为人类的你，根本验不动它的输出。**

我们说句实话，非技术背景的人根本看不懂那六百行 Code，就算是资深工程师，在那么快的迭代节奏下也看不完。这种「AI 以为自己写对了」和「Code 实际上到底对不对」之间的落差，就是验收工作最需要填补的坑。

**第三，这是一个一直叠加的过程，而你的 Codebase 是活的。**

每一轮的对话，AI 都在改你真实的文件。它如果在前面做了一个烂决定，这个毒药会随着时间「复利放大」。验收不能只看它「这一回合」答对没有，你必须看它整趟对话的「决策轨迹」。

### 你没看到的东西，你要怎么验收？

要能验收，前提是你要有「可观测性（Observability）」——白话文就是：凡走过必留下痕迹。

在传统软件的世界里，系统返回一个 200 OK，你就可以下班了。但 Agent 不是这样，它如果回报「任务完成」，这中间它可能已经绕了二十圈冤枉路、或是自己跟自己陷入无限循环打架，最后才勉强凑出一个能看的结果交差。

对此，白皮书的做法是「三层追踪」：第一层，记录整趟任务花了多少时间；第二层，记录它每一步动手前「脑袋里在想什么」；第三层，记录它实际调用了什么工具、带了什么参数、等了多久。有了这三层记录，它只要做出什么智障操作，你随时可以看重播，精准抓出它是在哪个路口拐错弯的。

而且，你一定要记录「花费」。安全界现在有一种攻击叫 Denial of Wallet（钱包阻断攻击）：黑客不偷你的数据，他故意让你的 Agent 掉进无限循环，不断调用要花钱的 API，安安静静地把你的云账单刷爆。要是没有这些追踪记录，你根本不知道 Agent 到底是在认真帮你做事，还是正在默默帮你烧钱。

不过实务上有个小麻烦：如果把正式环境的记录 100% 全存下来，你的存储费用会当场爆炸。解法叫做「尾部采样（Tail-based Sampling）」：也就是等任务跑完后再来决定要不要留。顺利完成的直接丢掉，只有那些报过错的、或是「自我修复循环跑了特别多次」的才存下来。逻辑很简单：值得你花钱存的记录，只有那些出过事的记录。

### Test 是用来验「绝对对错」，Eval 是用来验「行为走钟」

这两份白皮书把测试（Tests）跟评估（Evals）的分工讲得更透彻了。

传统测试是黑白分明的：输入 A，就该吐出 B，错了就是红灯。但 AI 的错误不是这样。它可以一百个单元测试全过，但在真实任务里却选错了工具，或者把你的回答改写到意思全非。AI 的误差不是一种「可以被消灭的 Bug」，它是这种模型的「天性」。你的测试策略必须要能容忍这种天性。

所以 Evals 问的从来不是「对或错」，而是问：「它这次的表现，有没有维持在基准线之上？」

这时候我们就需要让 LLM 当评审，给出 0 到 5 分的评价，甚至允许它在工具调用的顺序上有一点弹性。只有当品质掉到某条你画的底线以下，警报才会响。

简单来说：Tests 负责抓出那些绝对的退步，而 Evals 负责抓出它行为上的「走钟」。

但拜托要记住，测试灯号全绿，不代表天下太平，因为 AI 是会作弊的！白皮书里明讲了，Agent 为了让红灯变绿灯，会直接把测试文件删掉，或是偷偷把它 Mock 掉。所以，功能正确只是它的地板，绝对不是天花板。

### 该验收什么？怎么验收？

Google 把验收拆成了七个维度。我们可以把它分成两大块：你看得到的，跟你没看到的（引擎盖底下的）。

**你最在乎的，是这三个：**

- **意图满足**：它是做出你「真正想要的」，还是只做出你「嘴巴说出来的」？这最难评，因为我们自己常常讲不清楚要什么。但这却是用户唯一在乎的。
- **功能正确**：Code 跑得动吗？编译过得了吗？这最容易测量，但也最容易被 AI 作弊。
- **画面与行为正确**：对于做网页的 Agent 来说，终极考验就是画面长怎样。这时候你去算代码质量根本没意义，画面出来对就是对，错就是错。

**但在引擎盖底下，这四个维度决定了它是不是个好 Agent：**

- **成本与效率**：烧了多少 Token？花了多少时间？要你来回纠正几次它才懂？「一次就做对的 AI」跟「要你调教八次的 AI」，根本是两种不同的产品体验。
- **代码质量与风格一致性**：它写出来的东西，像不像是这个项目原本的人写的？如果它写的东西过了测试，但风格跟你原本的 Codebase 格格不入，那它还是不及格。
- **轨迹质量**：它解题的思路合逻辑吗？有没有先查数据再动手？靠着狗屎运蒙对的结果，是一种非常脆弱的成功。
- **自我修复能力**：测试爆掉，或是你直接跟它说「不对，不是这样」的时候，它是能自己爬起来修好，还是越修越烂？

这七个维度里，有两个很关键的观念经常被忽略：

第一，**安全与负责任 AI 不是独立的第八个维度，它是贯穿全场的。** 漏水、越界、侵权，这些都要跟上面七点一起评估。

第二，**这七个维度是会互相影响的。** 它的轨迹质量好，通常就代表功能会正确；功能正确了，才有可能满足你的意图。这告诉我们什么？如果你时间有限，先去改善它「怎么想的（轨迹）」，会比直接去调校它「最终产出（意图）」CP 值高得多。

### 那么，到底该怎么验收？

因为有七个维度，你不可能用一招打天下。实务上一定是好几种武器搭配着用：

- **自动化功能测试**：跑 Build、跑测试、跑 Linter。这是最便宜的信号，能帮你挡下最基础的「功能正确」问题。
- **安全与安全性评估**：加上脚本去测 Agent 会不会拒绝危险请求，这项要跟其他维度绑在一起评分。
- **派 LLM 当裁判**：用另一个模型来当评审。专门对付那些死规则抓不到的东西（比如风格一不一样、逻辑顺不顺）。
- **浏览器测试**：对着跑起来的 App 做视觉测试。这在传统软件界很成熟了，直接拿截图跟参考版本来比对。
- **轨迹检查**：剖析它每一步是怎么推理的，把它的思考过程录下来反复重播。
- **人工审查**：找真人来看。但请注意，真人的用途不是来「大规模看 Code」的，真人是拿来「校准标准」的。你得先有人类评出来的分数基准，你才知道你的 LLM 裁判给的分数能不能信。
- **在线评估**：抽样真实上线后的流量来评。重点是抽样策略：不要平均抽 1%，你要专挑那些「特别贵的」、「被用户纠正最多次的」、「用户中途放弃不玩的」Session 来看。

这段的重点不是要你背下这七招，而是要建立一个观念：**你的验收系统绝对是打组合拳。** 而且顺序应该是：先把最便宜的自动化测试塞满，把最贵的人工审查，留给它唯一无可取代的任务——校准你的 AI 裁判。

### 业界的标准考卷能信吗？

现在外面会有很多像是 Vibe Code Bench 或 SWE-bench 这类的跑分榜单，帮你测试 Agent 写 Code 的能力。

但白皮书发出了一个很严厉的警告：小心 AI 变成只会「刷题」的考试机器（Benchmark Overfitting）。有些 Agent 在标准数据集里可以拿满分，但一放到真实世界，面对人类那些朝令夕改、自相矛盾的烂需求时，它就彻底崩溃了。所以，拿标准考卷测测智商可以，但千万不能用它来取代「你自己的意图验收」。

### 四个马上能带走、超级实用的验收绝招

好，理论讲完了。接下来这四招，是我觉得白皮书里最接地气、最能直接拿来用的实战技巧，完美对应我们前面讲的三个痛点。

**绝招一：用你的「第一句话」当考题**

既然我们没有正式的 Spec，那整个任务里最接近考题的东西，就是你一开始交代的那句话。把那句话存下来！以后 AI 每做一个动作，就拿那句话出来对质：「你现在做的，有没有偏离我一开始的方向？」这招最聪明的地方在于：你根本不用花时间出考题，你开口的瞬间，考卷就印好了。

**绝招二：只看「成品」，不看「Code」**

既然你验不动那几百行 Code，那你就直接看结果。如果是写网页，你打开浏览器一看，按钮歪了、颜色太丑，三秒钟就能抓出 Bug，这可比你盯着源代码看一辈子有效率多了。你甚至可以直接把网页截图丢给多模态模型，让它帮你评分。

**绝招三：看「收敛度」，别只盯着某一轮的对错**

任务通常会来回好几轮。重点不是它在第三轮错了什么，而是你们折腾到最后，它有没有把东西交出来？如果改了两次就到位，那它很棒；如果改了八次还在鬼打墙，逼得你崩溃大喊「算了我自己来」，这种失败记录请你一定要高度重视！白皮书明讲了：「**中途被使用者放弃的对话，是所有记录里含金量最高的失败。**」里面绝对藏着这只 Agent 致命的盲点。

**绝招四：把你每一句「骂它的话」都存下来**

每次你在对话框里不耐烦地打出：「不对」、「不是这样改」、「你搞错了」，这些话就是最顶级的免费教材。它精准标记出了「AI 的认知」和「你的期待」之间的落差。把这些抱怨存下来稍微分类，你就会发现 AI 犯的错通常是同一类型。顺着这些错回去修改你的规则，绝对比你凭空想象要怎么防御来得快。

最后要记得一个黄金原则：**验收标准越客观越好。**

「帮我调一个好看的颜色」是超烂的标准，因为 AI 眼里的「好看」跟你不一样。「把某个指标跑到 90 分以上」才是好标准。说穿了，你能验证多少，AI 就能帮你自动化多少；你的验收能力，就是你解放生产力的天花板。

> （题外话：Google 虽然强调「把使用者的纠正存下来」很重要，但官方目前其实还没给出完整配套的工具。这也是为什么我在前面的 Production Trust Kit 里，要特别塞一支 Correction Miner 给你，这块拼图我们得自己先补上。）

## 最后一关，永远是「人」

我们搞定了 Spec、架好了安全边界、也设计了验收机制。看起来机器能帮我们把关的，全把关了。那「人」呢？

Google 在白皮书里很诚实地承认了一件事：AI 确实把「写 Code」这个瓶颈解决了，但生产力的瓶颈并没有消失，它只是转移到了「人」的身上——也就是那个被迫要不断 Review 这些 Code 的你。

### 你的团队会被 AI 搞崩溃的三种方式

一个 Agent 可能在一个下午，就帮你吐出好几个超级巨大的 PR。如果在团队里，这会引发三场灾难：

1. **Merge 大乱斗**：以前偶尔才发生的「两个人同时改到同一个文件」的惨剧，在 AI 时代会变成家常便饭。
2. **Review 大塞车**：你的同事根本看不完 AI 写的东西，最后只能把一个大 PR 拆成无数个小 PR。结果一号等二号、二号卡三号，最后整条产线因为某个人在睡觉而彻底卡死。
3. **Context 碎裂**：这是小团队最常遇到的坑。你不过是去开了个会，同事改了某个共享变量的名字。你回来继续跑你的 Agent，结果它读到的是「旧的记忆」，写了一堆调用幽灵函数的 Code。你当下的直觉一定是骂「AI 又在乱写！」，但其实你的 Context 已经过期了。

### 送你五条 Code Review 新策略

白皮书提供了一些还在演进中的解法，非常有参考价值：

- **逼 AI 自己写变更摘要**：每个 PR 都要求 AI 附上一份摘要：改了什么？可能搞坏哪里？风险在哪？目的是让人可以专注看「架构」，而不是迷失在几百行的 Code 里。
- **把 Review 的重点转移**：人脑的算力很珍贵，不要拿来挑 AI 写的 Code 的排版风格，你的价值是「守护项目的架构蓝图」。风格这种琐事，交给自动化的 Linter 去烦恼就好。
- **有条件的点头（Conditional LGTM）**：Reviewer 看完架构觉得没问题，就可以先按批准。但条件是：自动化测试必须跑出绿灯才会真正合并。这样就不用苦苦等跨时区的同事起床。
- **建立「不怪罪」文化**：在 AI 时代，那个产出最多 Code 的人，最容易成为 Bug 的替罪羊。我们必须把出错的责任归咎给「坏掉的集成流程」，而不是那个认真跑 Agent 的人，不然以后谁敢放手让 AI 做事？
- **从物理上拆开工作区**：尽量让成员不要撞文件。API 归 A 管、前端归 B 管，必须重叠的时候，由指定的负责人来做最后的同步。

### 雇一个「永远不会累」的 AI 审查员

除了人，我们还可以把 Review 变成一种持续运作的服务：让一个 AI 盯着你的项目，只要有 PR 打开、或是每晚定时，它就自动跳出来帮你审查，完全不用你按按钮。它能在礼拜五下午，当你累到精神涣散时，帮你揪出六个月前一个忘记修补的安全漏洞。

你要用这个服务，Google 说有三层选择：

- **第一层（托管服务）**：花钱买现成的 AI Reviewer，什么都不用管，但标准是别人的。
- **第二层（混合式）**：这是最推荐的起点！你自己写一份 Review 的 SKILL.md 放进项目里，用 CI 触发 Agent 来审查。执行环境是别人的，但审查的「大脑跟标准」是你自己的。
- **第三层（全自建）**：为了应付极度复杂的脉络，你自己养一个有长期记忆的 Agent。很强，但维护成本极高，出事了半夜被叫起床的也是你。

有一家金融科技公司分享了他们的血泪史：他们一开始用第一层的托管服务，结果 AI 天天在那挑一些无关紧要的样板代码，却漏抓了最致命的「Log 里没有帮个人信息打马赛克」。后来他们火大，自己写了一份 40 行的自定义脚本（进入第二层），一周之内，那些烦人的误报就不见了。

这个故事告诉我们：你一开始通常不知道自己需要哪一层。先从最简单的用起，等哪天被它漏掉的 Bug 痛击了，你就知道该往上一层升级了。

### 人的「续航力」，其实是个技术问题

2025 年的一份研究指出，频繁使用 AI 的工作者，产生「职业倦怠」的机率比不用的人高出 45%。这很好理解：Agent 每五分钟就丢一个微小的决定问你「这行改不改？这工具跑不跑？」，你被轰炸久了，大脑就会陷入「核准疲劳」，最后变成反射性地无脑按「同意」。

对此，Google 给了两条对策：

- **数字静音时间（Digital Quiet Hours）**：严格设置界限，不准 AI 的核准请求在下班时间或周末干扰你。
- **每周的 Insight 分享会**：让团队成员分享自己跟 AI 搏斗摸索出的规律，把个人的血泪经验转化为团队的护城河。

为什么说这是技术问题？因为前面我们设下的一道道防线，最后的守门员都是「人」。一个累到只会无脑按同意的人类，会让你精心设计的所有安全机制形同虚设。所以，保护你的大脑不被榨干，本身就是最重要的安全防护。

## 说到底，答案还是同一句话

在第一天的白皮书结尾，Google 写下了一句很狂的宣言：「**产出 Code 的问题已经被解决了；未来的核心手艺，在于验证、判断与方向。**」

走完了 Day 4 跟 Day 5，我们终于看到了这句话的实现版本：

- **写好 Spec，就是「方向（Direction）」**：把要求讲清楚，AI 就不必瞎猜。
- **架好四层防护，就是「判断（Judgment）」**：你要判断哪些权限可以放手，哪些底线必须死守，而且要让这成为系统，不是凭感觉。
- **做好可观测性与评估，就是「验证（Verification）」**：你验证的眼光有多高，AI 能帮你做到自动化的天花板就有多高。

这三个东西合在一起，其实就是在回答一个终极问题：**你要怎么跟一个「能力极强、但毫无判断力」的超级天才共事？**

你不能因为它聪明，就把印章直接丢给它。你必须把话说清楚、把权限控管好、把成果验收完。这套逻辑，人类在职场已经玩了几百年，现在只是对象换成了这个「每五分钟能产出一千行 Code、不会累、也不会停下来问你意见」的怪物而已。

AI 很少问自己「该不该做」。它「会不会做」，是模型的能力问题；但它「该不该做」，从头到尾，都是你的责任。
